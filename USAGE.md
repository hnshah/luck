# Using Luck Consistently

This repo now has two layers:

- luck.md - canonical theory and full framework.
- luck.runtime.md - compact agent runtime instructions for consistent use.

Use luck.runtime.md by default in live agent workflows. Use luck.md when you want the full conceptual model or citations.

Fastest local path:

    bin/luck-check --name "Thing to assess" --file templates/repo.md --mode fast

## When To Use It

Use Luck for:

- strategy choices
- repo or product feedback
- workflow design
- opportunity evaluation
- deciding what bottleneck to fix first
- diagnosing whether something will compound or fade

Do not use Luck for:

- routine coding
- simple summaries
- tasks with an obvious next step
- cases where speed matters more than diagnosis

## The Operating Ritual

1. Inspect real context first.
2. Run a Luck assessment.
3. Carry forward only three lines:
   - Binding constraint
   - Failure mode to avoid
   - Next test
4. Do the work.
5. At the end, ask whether the constraint changed.

This prevents framework performance. Luck should sharpen execution, not create a separate strategy ceremony.

## Minimum Context

For repo feedback:

- README or primary docs
- install or first-run path
- one observed friction point
- maintainer/user goal

For workflows:

- trigger
- inputs
- output
- manual rescue points
- what repeats or compounds

For product or strategy:

- current constraint
- active demand
- adoption path
- available resources
- what success makes easier next

## Quality Bar

A useful Luck output has:

- one clear binding constraint
- one concrete failure mode
- one next test that can be run soon
- little or no jargon
- no full seven-part scan unless explicitly requested
- a do-now / do-next / defer line

A weak Luck output:

- lists all seven checks without prioritizing
- sounds profound but does not change the next move
- recommends timing or moat work before solvency and adoption work
- has no test
